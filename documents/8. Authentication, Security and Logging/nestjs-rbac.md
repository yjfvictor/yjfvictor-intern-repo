# Role-based Access Control (RBAC) in NestJS

## Summary of the project

The [test-repo-for-RBAC-in-NestJS](https://github.com/yjfvictor/test-repo-for-RBAC-in-NestJS) project is a small NestJS API that shows how to implement role-based access control using Auth0. It exposes three message endpoints: a public one (no auth), a protected one (valid JWT required), and an admin one (valid JWT plus a specific permission in the token). The API uses Auth0 as the identity provider, validates JWT bearer tokens with the `express-oauth2-jwt-bearer` library, and uses NestJS guards to enforce authentication and permission checks. The project can be run locally or in Docker.

## How Auth0 stores and manages user roles

Auth0 stores and manages roles in its own system. You define roles in the Auth0 Dashboard (or via the Management API) and assign one or more permissions to each role. Permissions are scopes you define for your API (for example, `read:admin-messages`). You then assign roles to users. Auth0 does not put role names directly into the access token by default. When you enable RBAC for an API and turn on "Add Permissions in the Access Token", Auth0 puts a `permissions` claim in the access token that lists all permissions the user has from all their roles. So roles are managed centrally in Auth0, and the token your API receives contains the resulting permissions. Your NestJS app can restrict access by checking that the token’s `permissions` array includes the required permission (for example, `read:admin-messages`) rather than checking role names. If you need role names in the token, you can add them via an Auth0 Action as a custom claim (for example, a namespaced claim like `https://your-api.com/roles`).

## What is the purpose of a guard in NestJS?

A guard in NestJS decides whether a request is allowed to reach a route handler. It runs before the controller method and returns a boolean (or a promise that resolves to a boolean). If the guard returns true, the request continues. If it returns false or throws an exception, NestJS blocks the request and can send an error response (for example, 401 Unauthorized or 403 Forbidden). Guards are used to centralise authentication and authorization logic so you do not repeat the same checks in every controller. In this project, the AuthorizationGuard validates the Auth0 JWT and the PermissionsGuard checks that the token’s `permissions` claim contains the required permission. By applying these guards on specific routes or controllers, we ensure only authenticated and authorised users can access the admin endpoint.

## How would you restrict access to an API endpoint based on user roles?

To restrict access by user roles in this setup you do the following. First, in Auth0 you create an API and enable RBAC, then add a permission (for example, `read:admin-messages`) and create a role that has that permission. You assign that role to the users who should have admin access. You enable "Add Permissions in the Access Token" so the token includes the `permissions` claim. In NestJS you then use two guards on the endpoint: one that validates the JWT (so only authenticated users get through) and one that checks the token’s `permissions` array for the required permission. Only users whose Auth0 roles grant that permission will have it in the token and will pass the guard. Others receive 403 Forbidden. So restriction is done by required permissions in the token, which come from the roles you assigned in Auth0. If you prefer to check role names instead, you would add roles to the token via an Auth0 Action and then implement a guard that checks that custom claim.

## What are the security risks of improper authorization, and how can they be mitigated?

Improper authorization can let users access data or actions they should not. For example, a user might call an admin-only endpoint, see another user’s data, or perform destructive operations. Risks include privilege escalation, data breach, and non-compliance with policies or regulations. Mitigations include: enforcing authorization on every protected endpoint (do not rely on the client to hide or disable links), checking permissions or roles on the server using the validated token (never trust the client to send role or permission flags), using Auth0 RBAC so permissions are defined and assigned in one place, keeping the NestJS guard logic simple and consistent (for example, one guard that validates the JWT and one that checks required permissions), logging access attempts and failures for auditing, and applying the principle of least privilege so users only get the permissions they need. Regular review of roles and permissions in Auth0 and of the guards on each route helps keep authorization correct over time.
