# Reflection: Set Up AI Tools for Development

## Which AI tools did you try?

- **Cursor**. Used as the main IDE for this repository. Cursor is an AI-focused editor built on VS Code, so the layout and shortcuts are familiar, but it adds in-editor chat (a side panel where you ask questions or request edits with the current file or selection in context) and Composer (a flow for larger, multi-step or multi-file tasks where you describe a goal and the model proposes and applies changes). The assistant can read the open file, referenced paths, and often other parts of the repo, so it is useful for navigation ("where is X defined?"), refactors that touch several files, and documentation that refers to real code. In this project it was used to draft and rewrite markdown (e.g. this document), to refine task checklists and add real examples instead of stubs, to fix formatting and style, and to add or restructure sections. For pair programming on a single codebase with the need to edit multiple files or long passages, Cursor was the primary tool.
- **ChatGPT**. Used in the browser for one-off coding questions and for learning. Unlike an in-IDE tool, ChatGPT does not see your project by default, so it was used when the question was general (e.g. "how do I structure a README?", "what does this error message mean?", "how should I phrase a Git commit message?") or when comparing tools and concepts (e.g. "how does Copilot differ from Cursor?", "what is pair programming?", "what are IDE extensions?"). It was also useful for short explanations of a new library or API before opening official docs, and for brainstorming or step-by-step debugging when pasting a small snippet and the error text was enough context. For anything that needed to read or edit files in this repo, Cursor was used instead. ChatGPT was the go-to for quick, standalone answers without switching into the IDE.
- **GitHub Copilot**. Installed as an extension inside VS Code. It runs alongside the editor and offers inline code suggestions as you type: you see grey ghost text in the current line and press Tab to accept. That works for single lines, whole blocks (e.g. a function body or a test case), and sometimes for comments or docstrings. Copilot can also be used in chat mode from the editor to ask for snippets, refactors, or explanations without leaving the file. In practice it was used for quick boilerplate (e.g. repetitive config, type definitions, or stub functions), for unit tests (given a function name and signature, it often suggested assertion-style tests), and for filling in obvious patterns (e.g. mapping over a list, error handling). For long-form text like READMEs or design docs, Cursor or a separate chat tool was often preferred. Copilot’s strength is short, local completions rather than multi-file or document-level generation.

## What worked well? What didn’t?

### What worked well?

- **Cursor Composer for full-section rewrites**. Composer was useful for rewriting whole sections of documentation (e.g. a project README, a contributing guide, or a setup and troubleshooting section) without retyping everything. Asking for "real examples instead of stubs" produced concrete bullets that could be edited further. It was also helpful when the goal was to expand a short list into full paragraphs or to change the tone of a block of text (e.g. from informal to formal) while keeping the same structure. The ability to accept or reject edits in chunks made it easy to keep what worked and tweak the rest.
- **In-editor chat for small, targeted edits**. Chat worked well for tasks that were scoped to the current file or selection: fixing spelling and punctuation, changing a list format, or adding a short table. Because the model had access to the open file, it could make targeted edits without guessing. Examples that worked well included "capitalise the headings", "turn this paragraph into three bullet points", and "add a row to this table". For these, a single short prompt was usually enough and the result was quick to review.
- **AI for learning and explanations**. Using AI to explain concepts (e.g. "What is an IDE?" or "How does Copilot differ from Cursor?") gave clear, short answers that were good starting points before reading official docs. It was also useful for unpacking error messages (paste the message and ask "what does this mean and how do I fix it?") and for getting a minimal code example for a new API or library. The answers were not always complete or fully accurate, but they often reduced the time to find the right part of the documentation.
- **Structured output from a short prompt**. Asking for a checklist or a table (like the "AI Tools Overview" in this document) produced a usable structure quickly. Describing the columns or the type of items was enough for the model to generate a first draft. The result still needed a quick review for accuracy and tone, but it avoided starting from a blank page.
- **Iterative refinement**. When the first output was not quite right, following up with "make the bullets longer" or "add one more example for each" usually improved it. Breaking the request into steps (e.g. "first list the tools, then expand each with a paragraph") also helped when the initial response was too short or too generic.

### What didn’t work well?

- **Unclear or missing style instructions**. Without clear instructions, generated text sometimes drifted from the desired style (e.g. too casual or too long). Specifying style preferences (e.g. formal tone, no contractions) in the prompt improved the output. Similarly, when the task was underspecified (e.g. "improve this"), the model often made changes that did not match what was wanted. Stating the goal explicitly (e.g. "shorten this to three sentences" or "keep the same meaning but use simpler words") led to better results.
- **Project-specific logic and context**. For very project-specific logic or business rules, the AI sometimes guessed instead of using the codebase. It might suggest a function or a pattern that did not exist in the project or that conflicted with existing conventions. Pointing at a file with @ or pasting a short snippet reduced wrong assumptions. For decisions that depended on domain knowledge or organisational policy, the model was not a reliable source of truth and had to be checked against project docs or a human.
- **Vague or open-ended prompts**. Empty or vague prompts (e.g. "make it better") led to generic edits that often missed the real goal. Concrete requests (e.g. "rewrite this paragraph and add two example bullets") gave more useful results. Prompts that were too broad (e.g. "refactor this whole module") sometimes produced large, hard-to-review diffs. Narrowing the scope (e.g. "extract this function and add a unit test for it") made the output easier to evaluate and apply.

## When do you think AI is most useful for coding?

- **Boilerplate and structure**. Generating a README, a task list, a table of options, or the skeleton of a config file saves time. The model can fill in standard sections (e.g. "Installation", "Usage", "Contributing") or repeat a pattern (e.g. a row per tool, a bullet per step). The result still needs to be checked and adjusted for the actual project, but it avoids typing the same structure from scratch. This is especially useful when you know what you want the document or file to contain but not how to lay it out.
- **Documentation and comments**. Expanding a short outline into full paragraphs, or adding Doxygen-style comments to a function, is faster with AI. It helps to provide the desired style and an example so the output stays consistent (e.g. "use the same comment format as in utils.ts"). For long files, asking the AI to add or update comments for a selected block keeps the tone and level of detail under control. The main caveat is that the model may describe what the code does at a high level rather than capturing subtle behaviour or edge cases, so a quick review is still needed.
- **Explanations and learning**. When encountering a new library, error message, or concept, asking the AI for a short explanation or a minimal example often speeds up understanding. It can summarise a long doc page, suggest the next step when stuck on an error, or compare two approaches (e.g. "when would I use X instead of Y?"). Official docs and tutorials remain the source of truth for details and for correctness. AI is most useful here as a first pass before diving into the primary sources.
- **Refactors and rephrasing**. Rewriting a section for clarity, changing tone or punctuation, or splitting a long paragraph into bullets works well when the goal is stated clearly (e.g. "add real examples" or "use a formal tone"). The same applies to code: renaming variables for consistency, extracting a repeated block into a function, or converting a loop to a more idiomatic form can be delegated to the AI if you specify the scope and the style. Larger refactors (e.g. changing an entire module) are riskier because the model may not preserve invariants or may introduce subtle bugs, so smaller, reviewable steps are safer.
- **Repetitive or pattern-based code**. When the task is to repeat a similar structure many times (e.g. mapping over a list to generate config entries, or writing similar test cases for a set of functions), AI can generate the pattern and you fill in or adjust the specifics. This works best when the pattern is clear and the variations are small. It is less reliable when the logic is complex or when each case has different edge cases.
- **Less useful without guidance or context**. AI is less helpful when the task is underspecified, when the answer depends heavily on project-specific context the model cannot see, or when you need a single source of truth (e.g. a security or compliance decision). In those cases, human judgment and project docs should lead. It is also less useful when the problem is novel or when the correct approach depends on constraints (e.g. performance, compatibility) that are not stated in the prompt. Asking the AI to "figure it out" without enough context often leads to plausible but wrong or irrelevant suggestions.
