# Writing Unit Tests for Services and Controllers in NestJS

## Summary of the project

The project [test-repo-for-writing-unit-tests-for-services-and-controllers-in-nestjs](https://github.com/yjfvictor/test-repo-for-writing-unit-tests-for-services-and-controllers-in-nestjs) is a minimal NestJS application that demonstrates how to write unit tests for a service and a controller using Jest. The repository contains a runnable backend with a root controller and service, a single `GET /` endpoint that returns a greeting, and unit tests in TypeScript. The application can be started with `npm run start` and tested with `npm run test`. The service is tested in isolation with no mocked dependencies. The controller is tested with a mocked `AppService` supplied via NestJS testing utilities (`Test.createTestingModule` and a custom provider with `useValue`) so that the API handler is verified without depending on the real service. All source and test code uses explicit types and structured documentation. The codebase shows how to mock dependencies using NestJS's testing utilities and how to assert on both return values and mock call counts.

## Why it is important to test services separately from controllers

Testing services separately from controllers keeps responsibilities clear and makes failures easier to interpret. Services hold business logic (for example, computing a sum or building a message). If that logic is wrong, a unit test that targets only the service will fail at the point of the bug. If the same logic were tested only through the controller, a failing test would not tell you whether the mistake is in the controller (for example, wrong parameters or response handling) or in the service. Testing the service on its own also allows you to cover edge cases (zero, negative numbers, empty inputs) without setting up HTTP or routing. Controllers, in turn, can be tested in isolation by replacing the service with a mock. You then assert that the controller calls the service correctly and returns the service result. So services are tested for correct behaviour, and controllers are tested for correct use of the service and correct handling of the request and response. This separation makes the test suite faster, more focused, and easier to maintain.

## How mocking dependencies improves unit testing

Mocking dependencies improves unit testing by isolating the unit under test and controlling its environment. When you test a controller, you do not want the test to depend on the real service implementation, a real database, or external APIs. If the real service fails or changes, the controller test would fail even when the controller code is correct. By supplying a mock (for example, an object with the same method signatures that returns fixed values), you ensure that only the controller is exercised. You can then check that the controller returns the value coming from the mock and that it called the mock the expected number of times with the expected arguments. Similarly, when a service depends on another service or a repository, mocking those dependencies lets you test the service in isolation and simulate success, failure, or edge cases without touching real infrastructure. NestJS supports this through `Test.createTestingModule`, where you can list providers and override them with `useValue` or `useClass`, so that the dependency injection system injects your mocks instead of the real implementations. This makes unit tests fast, repeatable, and independent of external state.

## Common pitfalls when writing unit tests in NestJS

Common pitfalls include the following. Forgetting to `await` the result of `Test.createTestingModule({ ... }).compile()` leads to a promise instead of a module, so `moduleRef.get(SomeService)` fails or behaves unexpectedly. Using the real implementation of a dependency when you intend to mock it (for example, registering the real service in the testing module for a controller test) means the test is no longer a pure unit test and can fail for reasons unrelated to the controller. Not resetting mocks between tests (for example, with `mockClear()` or `beforeEach`) can cause tests to affect each other through shared mock state. Asserting on the wrong thing (for example, only checking that the controller returns a string without checking that it called the service) can miss bugs where the controller ignores the service or calls it with wrong arguments. Relying on the order of test execution or on shared mutable state makes tests flaky. Using `any` or skipping types in test code can hide mismatches between mocks and the real interface. Finally, testing implementation details (for example, internal private methods) instead of the public behaviour makes tests brittle when you refactor. To avoid these, always await `compile()`, use explicit mocks for dependencies, reset mocks when needed, assert on both return values and interactions, and keep tests independent and focused on observable behaviour.

## How to ensure that unit tests cover all edge cases

To ensure that unit tests cover edge cases, start from the behaviour of the unit and think in terms of inputs and outputs. List all parameters and possible values: zero, negative numbers, empty strings, empty arrays, null or undefined if the type allows it, and very large or boundary values. For each method, write at least one test for the "happy path" and then add tests for each distinct edge case. For example, for a function that adds two numbers, test both positive, both negative, one zero, and mixed signs. For a function that looks up a user by id, test a valid id, an invalid or missing id, and perhaps an empty string if the API accepts it. Use descriptive test names (for example, "should add two positive numbers" or "should return undefined when user is not found") so that when a test fails, the name explains what scenario broke. Group tests with `describe` blocks by method or scenario. If the logic has branches (if/else, switch), ensure each branch is exercised by at least one test. Code coverage (for example, `npm run test:cov`) can highlight untested lines or branches, but it does not replace thinking about edge cases. Review the code under test and ask what could go wrong or what inputs are special, and add tests for those cases. Over time, bugs found in production or in code review can be turned into regression tests so that the same edge case is always covered.
